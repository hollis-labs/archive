## Description

The current `/v1/context/promote` endpoint is a direct write from app namespace to user namespace. This is too permissive — it bypasses review and leaves no structured audit trail. This task introduces a gated promotion workflow by defining two new record types: `promote.request` and `promote.approve`. The actual enforcement is TASK-20260228-014.

**This task is spec + data model only** — define the record types, their required fields, and the namespace conventions for storing them. No enforcement logic yet.

**Record type: `promote.request`**

Stored in: `app/<id>/promotions/<request-id>`

Required fields (in metadata_json or payload):
```json
{
  "type": "promote.request",
  "source_namespace": "app/myapp/draft/pref-v2",
  "source_key": "pref-v2",
  "source_revision_id": "abc123",
  "source_checksum": "sha256hex",
  "target_namespace": "user/memory/preferences",
  "target_key": "user-prefs",
  "reason": "Updated user preferences after confirmation",
  "proposed_summary": "Brief description of what changed",
  "policy_rule_id": "policy-003",
  "requested_at": "2026-02-27T10:00:00Z",
  "requested_by": "app:myapp",
  "status": "pending|approved|rejected|applied"
}
```

**Record type: `promote.approve`**

Stored in: `user/memory/promotions/<approval-id>` (or `user/promotions/<approval-id>`)

Required fields:
```json
{
  "type": "promote.approve",
  "request_id": "...",
  "request_namespace": "app/myapp/promotions/req-001",
  "approved_at": "2026-02-27T10:05:00Z",
  "approved_by": "user",
  "notes": "optional approval notes"
}
```

**Outputs**:
1. `docs/SPECS/PROMOTION.md` — spec doc defining both record types, storage conventions, namespace rules, and the request→approve→apply lifecycle.
2. Updated `docs/SPECS/STORAGE.md` to reference the promotion workflow.
3. Go type definitions for `PromoteRequest` and `PromoteApproval` in `internal/contextstore/` (structs only, no enforcement logic).
