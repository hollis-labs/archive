## Description

The View spec (`docs/SPECS/VIEWS.md`) defines `tags_any` as a supported selector field, but `internal/contextstore/Select` does not implement tag filtering or indexing. This is a spec/implementation mismatch that will cause agent confusion: agents reading the spec will believe tag-based selection is supported when it is not.

**Decision to make**: This task requires a deliberate choice between two options before writing any code:

- **Option A (recommended for now)**: Remove `tags_any` from the View spec entirely. Add a comment: "Tag-based filtering is planned (see Phase 2 tag indexing task)." This is the safest path — it makes the spec accurate and defers implementation complexity.
- **Option B**: Implement minimal tag indexing immediately. Store `metadata_json` per record in SQLite; add a `record_tags(record_id, tag)` table indexed on `tag`; update `Select` to join/filter when `tags_any` is supplied.

**Recommendation**: Choose Option A now. Option B is tracked separately as TASK-20260228-012 (tag indexing in the Context Packets sprint). Doing both at once risks scope bleed.

**What this task does NOT do**: It does not remove tag support from the codebase — only the `tags_any` field from the selector spec. Tags as record metadata (stored in `metadata_json`) can remain.

## Acceptance

- [ ] `docs/SPECS/VIEWS.md` accurately reflects current selector capabilities — `tags_any` is either removed (Option A) or implemented with tests (Option B).
- [ ] If Option A: a comment in VIEWS.md notes that tag filtering is planned (links to Phase 2).
- [ ] If Option A: `internal/contextstore/Select` is unchanged.
- [ ] If Option B: `Select` correctly filters by `tags_any`; a `record_tags` table exists in the schema; tests cover the tag filter path.
