## Description

The `records` table has a `checksum` column and `internal/contextstore` already imports `sha256`, but `AppendRecord` inserts `checksum` as an empty string (`""`). This means no records written to date have a verifiable checksum, and the consistency scan cannot detect file corruption.

**What to implement**:

1. **In `AppendRecord`**: Compute `sha256(payload_bytes)` at write time and store the hex digest in `records.checksum`. The payload is the file body written to disk — compute the checksum from the same bytes before or immediately after writing the file.

2. **In the consistency scan** (`/v1/context/scan` or equivalent): When a record's file exists on disk, re-read the file, compute `sha256(file_bytes)`, and compare against `records.checksum`. If they differ, mark the record as corrupted in the scan result. If `checksum` is `""` (a legacy record), note it as "unverified" rather than "corrupted" — don't false-positive on old records.

**Important constraints**:
- Checksum is computed from the payload bytes, not the full record struct. Keep this simple and deterministic.
- Do not recompute checksums for existing records as part of this task — that is a separate maintenance job.
- The checksum is informational for now (corrupt records are flagged in scan output, not automatically deleted or blocked).

## Acceptance

- [ ] `AppendRecord` computes and stores a non-empty SHA-256 hex digest in `records.checksum` for every new record.
- [ ] Consistency scan compares file bytes to stored checksum when `checksum != ""`.
- [ ] Scan marks records as `corrupted` (file hash mismatch) or `unverified` (empty checksum) — never as `ok` when corrupted.
- [ ] Tests: write a record, manually corrupt the file on disk, run the scan, confirm the record is flagged as `corrupted`.
- [ ] Tests: write a record, run scan without modifying file, confirm record is flagged as `ok`.
