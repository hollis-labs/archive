## Description

Implement the Policy Manager UI flow using the website golden template as the baseline design. Covers three screens: policy list, policy detail, and policy edit form. The policy system is the mechanism that enforces namespace ownership, tier retention rules, allowed ops, and required schema fields — so the UI must expose these dimensions clearly without hiding their deterministic enforcement semantics.

**Starting point**: `.volon/templates/website-golden-template/policy-manager.html`, `policy-detail.html`, `policy-edit.html`

**API contracts to surface**:
- `GET /v1/namespace/policies` — list all policies
- `GET /v1/namespace/policies/{id}` — fetch single policy with all fields
- `PUT /v1/namespace/policies/{id}` — update a policy (show validation errors inline)

**Context for the agent**: Policies enforce the ownership boundary between `user/*` and `app/<id>/*` namespaces. The UI must make it crystal clear which namespace patterns a policy applies to, what operations are allowed, and what the retention/schema constraints are. Ambiguous edits (e.g., broadening a policy scope) should require explicit confirmation. Any save must display deterministic success/failure feedback showing exactly which fields were accepted or rejected.

## Acceptance

- [ ] Policy list screen renders all policies with namespace pattern, tier, and allowed_ops visible at a glance.
- [ ] Policy detail screen shows all fields: tier, retention, max_revisions, max_bytes_per_key, allowed_ops, required_schema, redaction rules.
- [ ] Policy edit form validates inputs client-side and surfaces server validation errors inline (not in a generic error banner).
- [ ] Save action provides deterministic feedback: confirmation shows which fields were written and their new values.
- [ ] No ambiguous state during edit — unsaved changes are clearly indicated; navigating away prompts confirmation.
- [ ] `required_keys` and `ownership` fields are prominently labeled with explanatory tooltips.

## Verification

- [ ] Manually test against a live CMS instance: list → detail → edit → save round-trip.
- [ ] Confirm that policy-denied states (actor mismatch, forbidden op) are surfaced with actionable messaging, not silent failure.
- [ ] Confirm read-only rendering is correct when the actor does not have write permission to the policy namespace.
